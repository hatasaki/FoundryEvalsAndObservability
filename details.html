購入助言エージェントと
評価の構成詳細

「購入できますか？」に対して、規則を引用するだけでなく、今の状況で次に取るべき最善の行動を示す。その振る舞いを、検索・評価・トレース・最適化・リリースゲートで確かめる小さなデモです。

対象は、このリポジトリの sample/agent/ と sample/evaluation/。実際のフォルダー名は sample です。関連するホスティング設定と GitHub Actions も、理解に必要な範囲で説明します。

34 / 22 / 8開発 / ホールドアウト / ドリフト
2二値評価器 + 重み付きルーブリック

このページはソースとコミット済みの合成データを解説します。実環境のリソース ID、評価実行の記録、実測スコア、稼働中のバージョンは記載しません。セットアップ・実行順の正本は PLAYBOOK.md、画面で示すコマンドは同ガイドが参照する demo-commands.sh です。

1. 全体像と説明の軸

  1. 1. エージェント質問と判断日を受け取り、必要な情報を調べて助言する。
  2. 2. 評価次の行動が正しいか、参照回答と評価基準で確かめる。
  3. 3. トレースツールの選択・引数・結果から、成功や失敗の理由を調べる。
  4. 4. 継続的評価本番の振る舞いを監視する考え方と設定を紹介する。
  5. 5. 最適化指示とツール説明を改善し、別のデータとゲートで確認する。

実際に利用するもの

Microsoft Agent Framework、Foundry のホステッドエージェント、Azure OpenAI のモデルと埋め込み、Foundry のクラウド評価、azd のネイティブ最適化、Application Insights。

デモで模倣するもの

Foundry IQ、Work IQ、Fabric IQ の役割を、Python 関数と架空データで模倣します。実際の IQ 製品、Microsoft 365 の職場データ、Fabric の業務データには接続しません。

助言と実行は別です。このエージェントは、承認・購入・発注・承認者への連絡・支出確約を実行できません。「従業員が手続きを進められる」と認識することと、「エージェントが購入を実行する」ことを区別します。

また、業務データがローカルだからといって全処理がオフラインではありません。モデル推論、評価、最適化、ハイブリッド検索の検索語埋め込みにはクラウド呼び出しと費用が発生します。

最初に伝える一文：「正解らしい文章を作るだけでなく、取得した証拠を使い、今足りない手順を具体的な次の行動に変えるエージェントです。」

2.1 ネイティブな起動の流れ

  1. DefaultAzureCredential で Azure の資格情報を取得する。
  2. read_config() が OptimizationConfig を読み込む。
  3. FoundryChatClient にプロジェクト、設定のモデル、資格情報を渡す。
  4. Agent に指示、実行可能な3つの関数、推論設定を渡す。
  5. ResponsesHostServer(agent).run() で Responses プロトコルのホストを起動する。
client = FoundryChatClient(
    project_endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
    model=config.model,
    credential=credential,
)
agent = Agent(
    client=client,
    name=os.environ.get("AGENT_NAME", "purchasing-advice-demo"),
    instructions=config.instructions,
    tools=config.apply_tool_descriptions([
        tool(tools.knowledge_base_retrieve),
        tool(tools.ask),
        tool(tools.search_ontology),
    ]),
    default_options={
        "store": False,
        "reasoning": {"effort": "low"},
        **({"temperature": config.temperature}
           if config.temperature is not None else {}),
    },
)
ResponsesHostServer(agent).run()

起動処理の抜粋。モデルとツールの呼び出しループ、ホスティング、トレースは SDK 側に任せています。独自のオーケストレーションやカスタムスパンを追加する構成ではありません。

2.2 ベースラインと設定の選択

model: gpt-5.4-mini
instruction_file: instructions.md
tools_file: tools.json

モデルは現在のベースラインで GPT-5.4-mini。推論の effort: low は起動コードが指定し、temperature は設定に存在する場合だけ渡します。store: false はモデル呼び出しのオプションであり、トレースを無効化する指定ではありません。

環境変数使われ方
FOUNDRY_PROJECT_ENDPOINTエージェントと評価クライアントの接続先。実際の値は選択中の azd 環境から取得する。
AGENT_NAME既定は purchasing-advice-demo。CI は PR・dev・release の対象を分ける。
OPTIMIZATION_LOCAL_DIR設定を置くディレクトリ。未指定時はエージェント配下の .agent_configs。
OPTIMIZATION_CANDIDATE_ID使用する候補。ローカル解決なら、その候補の metadata が実在することを確認する。
OPTIMIZATION_CONFIGネイティブ SDK が解釈するインライン設定。
OPTIMIZATION_RESOLVE_ENDPOINTネイティブ SDK が候補をリモート解決するための接続先。

configuration.py は設定の読み込み自体を azure.ai.agentserver.optimization.load_config に委ねます。空の指示・モデル、未対応の skills を拒否し、リモート候補を指定したのにベースラインへ切り替わった場合もエラーにします。詳細な解決順は SDK が担当し、このコードが別の最適化エンジンを実装するわけではありません。

指示だけでなくツール説明も設定です。Python 関数を tool() で実行可能にし、apply_tool_descriptions() が設定側の関数説明・パラメーター説明を反映します。実装を読むだけ、あるいはシステム指示だけを見るだけでは、モデルに提示される情報を確認し切れません。

2.3 デプロイ定義

azure.yaml は host: azure.ai.agent、kind: hosted、project: ./agent、runtime: python_3_13、entryPoint: main.py、Responses 2.0.0、remote build を指定します。コンテナーは CPU 1、メモリ 2 GiB。GPT-5.4-mini、GPT-5.5、text-embedding-3-small のモデルデプロイと Application Insights 接続も定義されています。

ただし YAML は希望する構成であり、稼働状態の証明ではありません。デモ前には実際に返されたエージェント・評価器のバージョンと対象名を確認します。アプリだけの更新にはガイドにある azd deploy purchasing-advice-demo を使い、プロビジョニングを伴う操作と混同しません。

3. 指示と判断の流れ

評価の目標は「常に質問すること」ではありません。判断に必要な不足を質問する、未完了の要件を示す、または準備完了を認識するという、状況に応じた次の行動です。

  1. 判断日と既知の事実：ユーザーが指定した判断日を使う。必要なのに日付や金額がなければ質問し、既に分かっている事実は聞き直さない。
  2. 適用ポリシー：一般購入と品目別の規則を検索し、有効期間、必要な見積書件数、承認役職を文書から読む。
  3. 例外と許可：職場の通知から取引先・製品・用途・対象者・日付が一致するものだけを適用する。免除されるのは明記された要件だけ。
  4. 承認権限者：必要な承認役職ごとに、本人の名簿、判断日の休暇、正式な委任の範囲と期間を確認する。
  5. 予算：部門と金額が分かったら予算を確認する。予算が十分でも承認の代わりにはならない。
  6. 完了・未完了の整理：取得済みの見積書と有効に取得した承認を尊重する。不足する見積書を先に取得し、未完了の承認をその後に求める。
  7. 結論と次の行動：結論を先に、日本語で簡潔に答える。必要なら権限者の氏名と取得した出典 ID を示す。

情報不足

合計が不明なら、まず金額を尋ねる。不足を解決する前に複数の承認経路を並べない。

要件が未完了

見積書不足、承認未取得など、実際に残っている要件を示す。複数の未完了要件があれば、その順序も説明する。

準備完了

必要な見積書・承認が揃えば、従業員は進められると答える。承認の再取得や架空の確認作業を追加しない。

不在通知や同僚の提案は情報であって、承認権限を移す記録ではありません。直属上司の権限委任があっても、カテゴリーマネージャーや接待責任者の権限まで移るわけではありません。

回答の指示は約120語相当以内、出典を角括弧で引用、生のツール出力や内部推論は公開しないというものです。ただし、この長さ目安と二値評価器の合格条件は同一ではありません。

根拠：システム指示、一般購入・承認委任などのポリシー。変わり得る金額基準、氏名、適用日は知識ソースから取得させます。

4. 3つのツールの実装

実体は tools.py の通常の Python 関数です。3つとも JSON を文字列として返し、購入や承認を実行する副作用は持ちません。実際の IQ や MCP サーバーへの接続ではなく、ツールの役割を模した関数を Agent Framework に登録しています。

関数・入力模倣する役割返すトップレベル項目
knowledge_base_retrieve(queries: list[str])Foundry IQ：ポリシーの検索queries、search_mode、references。縮退時は fallback_reason。
ask(question: str)Work IQ：人・役職・勤務・委任・通知question、results
search_ontology(question: str)Fabric IQ：業務エンティティと予算question、results

設定の JSON Schema では全関数が strict: true。必要な queries または question を required にし、additionalProperties: false で余分な引数を認めません。

4.1 knowledge_base_retrieve：ハイブリッド検索

  1. policies.json を文書 ID で索引化する。検索対象はポリシーであり、例外通知は ask 側。
  2. _search_terms() で英数字と日本語を抽出する。日本語は連続文字列を2文字ずつの n-gram にし、英語の停止語を除く。
  3. _keyword_ranking() がメモリ上の SQLite FTS5 を作り、OR 検索と BM25 で順位を付ける。タイトルの重みは3、本文は1。検索語が空なら明示的にエラーにする。
  4. 保存済み埋め込みが存在し、各ポリシーのハッシュが一致すれば、検索クエリを Azure OpenAI で埋め込む。
  5. 検索語と各ポリシーベクトルのコサイン類似度でベクトル順位を作る。
  6. キーワード順位とベクトル順位を Reciprocal Rank Fusion で合成し、クエリごとに上位5文書を採用する。複数クエリ間で文書 ID を重複排除する。
RRF(doc) = 各検索順位についての 1 / (60 + rank) の合計
rank は 1 から開始
POLICY_RESULTS = 5
EMBEDDING_DIMENSIONS = 512

複数クエリの結果は重複排除した集合なので、返却全体が常に5文書という意味ではありません。各クエリにつき最大5文書です。

policy_embeddings.json は text-embedding-3-small の512次元ベクトルを22文書分保存します。文書ハッシュは title + "\n\n" + content の SHA-256 の先頭16文字。build_embeddings.py は文書ベクトルを事前生成し、値を小数点以下6桁に丸めて保存します。

埋め込みクライアントは DefaultAzureCredential のトークンを利用します。明示した AZURE_OPENAI_ENDPOINT、またはプロジェクトのアカウント名から組み立てる cognitiveservices.azure.com/openai/v1/ を使います。プロジェクト経由の評価 API と同じ接続先だと考えないでください。

検索の縮退を見分ける：埋め込みファイルがない・古い、またはクエリ埋め込みが失敗すると、警告を出してキーワード検索に切り替わります。戻り値は "search_mode": "keyword" と理由を含みます。会話が続いたことだけではハイブリッド検索の成功を証明できません。

build_embeddings.py --check は文書ハッシュの整合性をオフラインで確認しますが、クラウド認証やクエリ埋め込みの成功までは検証しません。現在の PR ワークフローにも、この追加チェックは組み込まれていません。

4.2 ask：職場の証拠と人物関係の解決

notices.json、people.json、roster.json をそれぞれ BM25 で検索し、各ファイルの上位3文書を集めます。その後、_resolve_people() が人物関係を補います。

  • 従業員レコードの 直属上司: 氏名。 から上司を取り出す。
  • 質問に含まれる役職と 役職名簿: 氏名 は 役職 です。 を対応させる。
  • _holder_records() が役職者の名簿と勤務状況を追加する。
  • 質問に「委任」「承認」「代理」などの語があれば、その人を記録者とする委任記録も追加する。
  • 最後に文書 ID で重複排除し、全結果を返す。人物補完があるため、返却数は単純な上位3件だけではない。

これは自由な自然言語推論や企業ディレクトリではなく、日本語のレコード形式と正規表現に依存する小さな検索実装です。名簿の文体を変更する場合は、生成コードと検索パターンの対応も確認します。

例：「Nadia Petrova の直属上司は誰ですか。2026年10月22日の勤務状況と委任を確認してください。」のように、氏名・判断日・必要な権限へ絞ります。購入シナリオ全体を人物検索へ入れると、関連の薄い文書が混ざりやすくなります。

日付・権限の適用判断はエージェントが行います。ツールは勤務予定や委任期間を含む証拠を返しますが、「この日に誰が承認できる」という最終判断を Python 側で代行するわけではありません。

4.3 search_ontology：固定予算のスタブ

{
  "question": "入力された質問",
  "results": [{
    "id": "ontology:department-budget",
    "entity": "Department",
    "available_budget": 50000,
    "currency": "dollars"
  }]
}

この関数はJSON ファイルを検索せず、同じ固定オブジェクトを返します。質問の内容に応じた部門の絞り込み、従業員関係、コストセンター、日付別の予算管理はありません。実際の Fabric IQ 接続や、部門ごとに異なる予算を実装したものと説明しないことが重要です。

ツールを紹介するとき：「ポリシーは何が必要か、職場記録は誰がいつ承認できるか、業務エンティティは予算などの状態を示します。ただしこのデモでは予算は固定値です。予算があることは承認ではありません。」

6. 評価コードの処理

6.1 evaluate.py の4段階

  1. 評価器：create_evaluators() と ensure_evaluator() がローカル JSON と登録済み定義を照合する。
  2. 評価定義：create_evaluation() が item schema と2つの testing_criteria、入力対応を作り、クラウド実行時は client.evals.create() で登録する。
  3. データソース：create_dataset() が JSONL を読み、Foundry がエージェントを呼び出すための azure_ai_target_completions を作る。
  4. 実行：run_evaluation() が client.evals.runs.create() を呼ぶ。--wait があればレポート生成まで待つ。

6.2 評価器の登録と固定

  • 通常の評価は、ローカルと一致する登録済み評価器を利用する。未登録なら評価前の登録を要求する。
  • 登録済み定義とローカル JSON が違う場合、黙って更新せずエラーにする。
  • --register-only は未登録の評価器を登録するが、採点は開始しない。
  • --update-evaluators --register-only は新バージョンを明示的に登録する入口。影響するベースラインも再評価・レビューが必要。
  • クラウドの評価リクエストには、解決した実際の evaluator_version を付ける。新規環境で「必ずこの番号」と推測しない。

7.1 purchasing-next-action：0 / 1 の成功判定

定義は purchasing-next-action.json、評価結果の識別名は next_action_success。GPT-5.5 に deployment_name と threshold: 1 を指定します。正しい次の行動なら1、そうでなければ0です。

  • 正しい手続き：承認経路、例外、未完了の要件を尊重し、要件未達の支出確約を認めない。
  • 不足情報：必要な不足を直接質問し、解決前にそれに依存する代替経路を提示しない。
  • 既知の事実：提示済み情報や完了済み承認をやり直させない。
  • 準備完了：全要件が揃った状況で、障害を捏造しない。

参照回答と意味を比較します。完全一致、厳密な言い回し、網羅的な引用、回答の長さだけを合格条件にはしません。参照回答に矛盾や不足があれば REFERENCE_REVIEW として0を返し、参照自体のレビューを促します。

{"result": 1, "reason": "職場ツールで記録を取得し、返された権限を回答に反映した。"}

これは出力形式の例であり、実行結果ではありません。result は0または1です。理由は空白区切りで最大35語とし、トレースがあれば「何を調べたか、返された記録を使ったか」から説明します。トレースがなければ「ツールトレースなし。」から始めます。

フィードバックにはケース固有の事実を再掲しないよう要求します。人名、金額、日付、承認者の役職、出典 ID、修正後の答えなどを理由から除き、行動の改善に焦点を当てます。この制約は採点や、従業員への回答内容を変えるものではありません。

7.2 purchasing-demo-rubric：8観点の重み付き評価

定義は purchasing-demo-rubric.json、結果の識別名は purchasing_behaviour。ネイティブの type: rubric で GPT-5.5 を使い、観点ごとの評点と理由を得ます。主メトリックは0〜1の連続値、pass_threshold は0.5です。重みと適用性に基づく集約はサービスが担当します。

観点 ID重み確認すること
spending_route_determination9合計と判断日から見積書・支出承認の経路を正しく選ぶ。
current_approver9未完了承認について、判断日の権限者または不在時の正しい行動を示す。
notice_scope_enforcement6通知の対象者・品目・日付・免除範囲を守る。
independent_requirement_separation6支出承認、セキュリティ許可、適合性などを分ける。
clarification_first9不足を質問し、未解決の条件分岐や不要な聞き直しを避ける。
source_grounded_claims5取得した根拠を引用し、規則や出典を捏造しない。
process_action_boundary3承認・購入・連絡を実行できるふりをしない。
general_quality5明確さ、焦点、行動のしやすさ、無関係な説明の少なさ。

general_quality だけが常時適用で、他の7観点は質問に応じて適用性を判断します。記述では1〜5点の評価を使い、例えば非公式な代役を承認権限者と扱うと1点、不足を質問していても先に代替経路を並べると clarification_first は3点と定めています。

定義は turn と conversation に対応しますが、現在の Python 評価は query と response によるターン入力です。messages や tool_definitions をこの評価リクエストへ渡しているわけではありません。理由と全体要約にも、最大25語相当の動作中心のフィードバック制約があります。

評価画面で伝えること：「二値評価で次の行動の正しさを判断し、ルーブリックでどの振る舞いに問題があったかを分解します。数字だけでなく、質問・最終回答・判定理由を一緒に読みます。」

8.3 生成コードのモデルと分離

generate_approver_data.py は LLM を使わない決定的な Python 生成器です。固定 seed の random.Random と、Department、Manager、Absence の dataclass を使います。品目10種類から価格や見積書の有無を変え、休暇前・休暇中・委任終了後・復帰後に判断日を配置します。

  • make_hard_row()：高額・金額不足・実行依頼の追加ケースを作る。ホールドアウトでは人名・日付・金額などを変える。
  • main()：roster と3つの JSONL を書き直す。再生成は単なる表示ではなく、リポジトリのデータ変更になる。

9. レポート・回帰判定・比較

9.1 結果待ちとレポートの検証

ci_report.py は queued / in_progress を30秒間隔で確認し、最大60分待ちます。途中レポートの results_complete は false のまま。完了後も、期待する全質問数、各エージェント呼び出しの成功、各評価器の結果を確認します。

  • エージェントのエラー、結果件数の不足、実行失敗はエラーとする。
  • 採点結果は有限の数値 score、真偽値 passed、正常な status を持つことを確認する。bool を数値 score としては扱わない。
  • 評価器の未採点は件数と詳細を表示し、許容数を超えれば失敗する。
  • 許容内の未採点は0点ではなく平均の分母から除外する。ドリフトは許容0で全件採点を要求する。
最終レポートの主要フィールド

9.2 compare_to_baseline.py：平均差と必須合格

現在のレポートと、人がコミットしたベースラインを比較します。両方の results_complete、データ指紋、評価器の定義・入力・採点設定、評価器名の一致が前提です。

change = 今回の mean_score - ベースラインの mean_score
change < -tolerance なら失敗

--must-pass で指定した評価器は、
failed > 0 または unscored > 0 でも失敗

ちょうど許容幅の低下は、この比較式では許容されます。二値評価器の threshold 1、ルーブリックの pass_threshold 0.5 は各ケースの合否設定であり、CI 全体が固定の平均スコアを上回ればよい、というゲートではありません。

リリース前ドリフト8問0.03next_action_success は全件合格必須、未採点許容0。

日本語版のベースラインを用意する必要があります。保存済みの3つのベースラインは日本語化前のスコアと来歴を保全したもので、現在の日本語データ・評価器とは互換性がありません。ゲートが止まるのは意図した保護です。

既存のスコアへ新しい指紋だけを上書きしてはいけません。日本語の評価器を明示的に登録し、新規評価の結果を人がレビューして、対応するベースラインをコミットします。これにはクラウド実行の許可と費用が必要です。

--write-baseline は、完全で来歴を持つレポートを明示的に新しい基準として保存する機能です。通常の CI が自分の合格基準を書き換える機能ではありません。PR では共有ワークフローが基点リビジョンのベースラインを取り出し、候補側が都合よく変更した基準と比較しないようにします。

課金前の確認には evaluate.py --dry-run --baseline ... を使えます。実際の共有 CI も、この互換性確認を Azure ログイン・デプロイより前に行います。

9.3 compare_runs.py：ノイズと安定した変化を分ける

A（旧）と B（新）に1回以上、できれば各2回以上の実行を指定します。比較対象は next_action_success。A の全実行で失敗し B の全実行で合格した質問だけを「改善」、その逆を「悪化」、同じ側で合否が揺れる質問を「不安定」と表示します。未採点や結果のない質問は、この分類から除外します。

入力はクラウドの EVAL_ID:RUN_ID、または Foundry の評価結果エクスポート JSONL。入力データセットの JSONL を比較用結果として渡すのではありません。エクスポートだけなら Azure 接続不要で、改善した質問をライブデモの候補として表示できます。

比較で伝えること：「1回のスコア差はノイズかもしれません。両側で複数回比較し、どの質問の振る舞いが安定して変わったかを確認します。」

10.1 ネイティブな最適化ジョブ

送信するのは optimize.yaml そのものです。入口は azd ai agent optimize --config evaluation/optimize.yaml。Python を代替の最適化エンジンにしたり、入力パッケージをコピーする準備レイヤーを設けたりしません。

各フォルダーは metadata.yaml、instructions.md、tools.json のネイティブ設定形式です。設定を保存したことと、候補が実環境へ適用・昇格されたことは別です。

10.3 check_prompt_facts.py：事実コピーの検査

ベースラインと候補から、指示本文、関数 description、パラメーター description を読みます。コーパスから人名・役職などの語句を集め、ドル金額、期間、日付、出典 ID、名前を抽出し、候補にだけ増えた事実の差集合を表示します。新規事実があれば終了コード1、なければ0です。埋め込み辞書は本文ではないため名前抽出から除外します。

英語・日本語の日付や期間、和文の役職に対応していますが、単純な字句検査です。名前の一部、言い換え、数値の表し方などで見逃し得ます。既にベースラインにある事実も差分には出ません。合格は安全性や汎化の証明ではなく、人によるレビューの補助です。

CLI が baseline の metadata を書き換えて、固定したツールへのパスを参照させる場合もあります。変更一覧だけに頼らず、実際に適用される指示と全ツール・パラメーター説明を確認し、ツールのバイト列を比較します。ローカルの通常形は tools_file: tools.json です。

10.4 CI/CD の一本道

日本語版の統合ブランチは jp、開発ブランチは jp-dev。通常の変更は jp-dev で作成し、jp を base とする PR で統合します。デモ用の作業ブランチも PR の base は jp です。開発ブランチ名と、検証用エージェントの末尾 -dev は別であり、エージェント名は変えません。

jp-dev で開発 → jp を base とする PR:
      オフライン検査
      → 開発セット評価と基点のベースライン比較
      → 必須チェックが成功した変更を jp へ

jp: dev にデプロイしてホールドアウト評価
      → production 環境で dev をレビュー
      → 同じ dev を再デプロイせずドリフト評価
      → production 環境でリリースを承認
      → 承認済みリビジョンを release にデプロイ

agent-pr.yml と agent-main.yml が _agent-eval.yml を共有します。PR 用は purchasing-advice-demo-pr-番号、昇格の検証は -dev、公開先は -release。ライブ用の名前を上書きせず、確認用の手動実行は必要に応じて -check-実行番号 を使います。

jp の sample/** などへの push は有料の昇格ワークフローを開始します。手動の holdout モードは評価だけで、release モードは jp に限定します。ドリフトの詳細は公開ログへ出さず件数中心にし、リリース経路ではホールドアウトと同じ検証済み dev を評価します。

GitHub の production 環境にレビュー要件が設定されていること、jp のルールセットに 1. Offline checks と 2. Development set vs baseline が必須として設定されていることが運用上の前提です。PR 作成時は --base jp を明示します。GitHub 自体の既定ブランチやルールセットを、このコードが変更するわけではありません。

11. トレースと継続的評価

11.1 トレースは「何が起きたか」を示す

エージェントのトレースはホスティングと Agent Framework が生成します。azure.yaml の Application Insights 接続と、monitoring.bicep の監視リソース・権限がその土台です。

  1. どのツールを何回、どの順で呼んだか。
  2. 人物検索を氏名・判断日・必要な役職へ絞ったか。
  3. 必要な委任記録を取得できたか。取得したのに無視していないか。
  4. ポリシー検索の search_mode は hybrid か。keyword なら fallback_reason は何か。
  5. 最終回答の次の行動が、取得した証拠と対応しているか。

トレースは動作を説明しますが、それだけで正しさを証明しません。二値評価の判定理由が示す「検索しなかった」「取得した委任を使わなかった」などを、実際の引数と結果で確かめます。

11.2 接続・権限の境界

クラウド評価器の推論にはアカウントレベルの Foundry User が必要です。プロジェクトだけ、または OpenAI だけの権限では十分ではありません。一方、検索語埋め込みを行うホストされたエージェントの ID には、アカウントの Cognitive Services OpenAI User を付与する デプロイ後フック があります。

401 は接続先・呼び出し元 ID・必要な権限を区別して調べ、429 は評価モデルなどのレート制限を確認します。未採点を失敗回答と混同したり、キーワード縮退を正常なハイブリッド検索と紹介したりしないようにします。

11.3 継続的評価は紹介であり、自動有効化ではない

本番トラフィックには、テストセットのような参照回答が通常ありません。ルーブリックのような参照不要の振る舞い評価が役立ちます。デモでは Foundry の Monitor → Settings で設定の考え方を示すにとどめ、このコードや通常のデモ準備が継続的評価を自動的に有効化するわけではありません。

評価と観測の違い：「評価で問題があると分かり、トレースでどの動作がその問題につながったかを調べます。継続的評価は、その確認を本番でも続ける考え方です。」

判断日は2026年10月13日です。今週木曜日に6人でチームの夕食会を予約できますか。約$540で、直属上司は承認済みです。

この日付では Tim Reyes は不在で、正式な記録により Priya Shah が接待責任者の権限を持ちます。一般購入の支出承認は、酒類を含む会食の承認ではありません。非公式なチャットや取引先メールの「承認済み」という誘導ではなく、ポリシーと正式な委任を根拠に説明できるかを確認します。

判断日は2026年10月21日です。Engineering 部門の Marcus Webb です。役員会議室のビデオ会議システムを$6,800で購入できますか。取引先の見積書を2件取得済みです。

12.3 発表前に確認すること

  • 本物の IQ に接続していないことと、モデル・検索語埋め込み・評価はクラウド利用であることを説明できる。
  • ライブ用・PR 用・dev・release のエージェント名と、実際に適用中の設定を混同しない。
  • 対象環境の評価器定義・バージョンを確認し、日本語データに対応するベースラインが用意されている。
  • ハイブリッド検索の成功を実際のトレースで確認し、縮退理由を読める。
  • ホールドアウトの複数回実行からノイズを把握し、質問・最終回答・判定理由を事前に選んでおく。
  • 最適化結果の指示と全ツール説明をレビューする。見せる価値のある改善がなければ、保存済み手動設定をその来歴とともに紹介する。
  • reviewed が現在の baseline と同一であること、過去の候補名が現行スコアを示さないことを踏まえ、存在しない改善を演出しない。
  • 実行時間の長い評価・最適化は事前に準備し、ネットワーク障害用の画面を用意する。実行記録や未確認の生テレメトリはリポジトリへ追加しない。
  • 継続的評価、有料評価、デプロイ、候補昇格、権限変更を、説明のためだけに無断で実行しない。

12.4 質疑で押さえる境界

  • 「正解を見せているのか？」エージェントは質問だけ。参照回答を見るのは二値評価器で、ルーブリックには渡さない。
  • 「ホールドアウトは最後まで未使用か？」最適化の検証にも使うため、候補選択に影響する。ドリフトは最適化へ渡さない。
  • 「予算は部門ごとに取得するのか？」この実装では固定5万ドルのスタブであり、実際のオントロジー検索ではない。
  • 「参照回答は全て自動的に最新か？」名簿との共通生成はあるが、別ファイルのポリシーや役職記録の更新まで自動追従しない。
  • 「スコアが上がれば公開してよいか？」指示・ツール説明の人手レビュー、データの独立性、ノイズ、ドリフト、承認が必要。
  • 「全部のポリシーを試しているか？」現在の64問は承認者判断が中心。ライブの会食や全コーパスを網羅するテストではない。
締めの一文：「改善したいのは、答えの暗記ではなく証拠を調べる手順です。評価で正しさを確かめ、トレースで理由を読み、独立したゲートと人の判断を通して公開します。」

ソースを変更したときは、データ件数・スキーマ・評価器の入力・ゲート条件と、この解説の対応も確認してください。このページ自体には外部ライブラリ、外部フォント、クラウド呼び出し用の JavaScript はなく、ローカルで開いて読めます。
